# Reverse engineering notes

What the Olight app is, and why the integration is shaped the way it is. Everything here was
established by static analysis of the shipping Android app; no traffic was intercepted and no
account was used.

## The app is a Tuya (ThingClips) app

The controlling app is the main **Olight** app, package `com.olight.omall` (v3.2.2 at the time of
writing). There is no separate "the Olight app" app — the smart-charger features live inside the shopping
app. It is built wholesale on the **ThingClips / Tuya** smart-home SDK.

Evidence from the APK:

- The whole `com.thingclips.smart.*` biz-bundle stack (device activator, panel, OTA, IPC camera,
  scene, family) is present as `META-INF/optimus/*` and `META-INF/thing/*` module descriptors.
- Native libraries shipped in `lib/arm64-v8a/`:
  `libthingsmart.so`, `libthing_security.so`, `libthing_security_algorithm.so`,
  `libThingSmartLink.so` (pairing), `libthingmmkv.so` (encrypted key/value store),
  plus the `libThing*SDK.so` camera/audio stack for Olight's camera products.

The practical consequence: the Ostation speaks the **standard Tuya LAN protocol** (port 6668,
protocol 3.5), which is what `tuya-local` and this integration target. The community confirmed the
Tuya product id `rcj4z3pdmhkzflio` for the Ostation 2 / 2 Pro.

## Where the local key lives

The Tuya LAN protocol encrypts every session with a **16-character local key that is unique to each
device**. The bytecode shows exactly how the app handles it:

- `LocalKeyBean`, `getLocalKeyByDeviceId`, `getEncryptLocalKeyWithDevId`, `getEncryptLocalKeyWithData`
  — the key is stored **encrypted, keyed by device id**.
- `refreshLocalKey(): encrypted key is empty` — when the encrypted cache is empty, the app fetches
  the key afresh. It comes down from the Tuya cloud during login / device sync.

So the local key is **generated by the Tuya cloud at pairing time and cached, encrypted, inside the
app**. It is not embedded in the app, not derivable from the device id, and not something the device
will hand out over the LAN — the station only ever *uses* the key to decrypt what you send it.

## Why network sniffing is not the easy path

The app enables **certificate pinning** (`okhttp3.CertificatePinner`, `SSL_PINNING_TYPE_*` in the
bytecode). A plain man-in-the-middle proxy — mitmproxy with a trusted root — will not see the key
exchange; it needs a pinning bypass (Frida/objection), which in turn needs a rooted or instrumented
device. That makes sniffing the *harder* route, not the easier one.

## Conclusion: what "fully local" can and cannot mean

- **Runtime is fully local.** Once Home Assistant has the local key, it talks to the station over
  the LAN on port 6668 with protocol 3.5. The station never needs to reach the internet, and you
  can block it at the router. This integration adds no cloud dependency of any kind.
- **The one-time key acquisition is the catch.** Because the key is cloud-issued and stored
  encrypted on a device, there is no way to obtain it purely from software with no device in the
  loop. The genuinely local options are, in order of effort:
  1. **Android emulator + logcat** — run the app in an emulator on any machine with virtualisation,
     sign in, read the key from the Tuya SDK's log. See [GET-LOCAL-KEY.md](GET-LOCAL-KEY.md).
  2. **A borrowed Android phone + logcat** — the same, on real hardware, for ten minutes.
  3. **ESPHome reflash** — replace the Tuya Wi-Fi module's firmware and drop Tuya entirely. Truly
     local forever, but almost certainly needs opening the unit and a serial connection on 2025
     firmware; not recommended as a first step.

  A one-time Tuya IoT cloud lookup ([tools/get_local_key.py](../tools/get_local_key.py)) is the
  least-effort route and leaves runtime fully local, but it does touch Tuya's cloud once, so it is
  offered only as an optional shortcut.
